# Routing runtime testing release: 0.1.40-beta.routing.0

[简体中文](0.1.40-beta.routing.0.zh-CN.md) · [Routing API](../mini-app-routing.md) · [Versioning](../versioning.md)

**Prepared for testing; not yet published (2026-10-29).** This independent
runtime-only prerelease uses npm tag `routing`. Stable `latest=0.1.39` and the
separate sensor/map `next=0.1.40-next.4` channel stay at their existing identities.
Stable `0.1.40` remains unpublished. This source includes Mini App routing only;
it does not merge or export device-sensor or street-map APIs.

The version is `0.1.40-beta.routing.0`, rather than `0.1.40-routing.0`: `beta`
sorts below `next`, so it is below the existing `^0.1.40-next.4` lower bound.
Test consumers must install the exact prerelease version in isolated branches.
Do not change stable production consumers or rely on a moving tag/range.

## What is tested

Standalone Apps use `useMiniAppRouter()` for App-relative paths, immutable
decoded segments, queries and push/replace/back. Hosts own browser or memory
adapters. SDK routing version/export checks run when the compatibility-shim hook
is invoked, and the hook requires an injected adapter. Source checkers detect
common static routing imports, default SDK aliases and SDK reexports; this is
not a general JavaScript data-flow analysis. Runtime contract version 1,
`sdkFeatures.miniAppRouting=1`, existing wallet/contract permissions and manifest
schema remain unchanged. See [the API guide](../mini-app-routing.md).

## Build and publication gates

Only `@flapsdk/vault-runtime`, version `X.Y.Z-beta.routing.N`, and the exact
fetched official `flap-sh/flap-vault-component-template` branch
`feat/mini-app-routing` are accepted. The source must be clean and committed.
Fork maintainers select the official `upstream` remote explicitly:

```bash
FLAP_TEMPLATE_FRESHNESS_REF=upstream/feat/mini-app-routing yarn runtime:package:routing
yarn runtime:verify-package
```

The dedicated command accepts no folders, canary flags or freshness-skip/sync
flags. The first release is permitted only after the fixed public npm registry
returns a genuine HTTP 404 for `routing`, dist-tags contain no `routing` entry,
and the exact target version also returns HTTP 404. The source must contain a
valid published npm latest `gitHead`; latest metadata must agree with dist-tags.
Redirects, timeouts, authentication failures, other HTTP errors and malformed
metadata fail closed. Later releases compare their own routing version and
must contain the published routing `gitHead`; they do not compare against next.

Review and push source to the official routing branch before running those
commands. A local preparation branch cannot satisfy the exact-ref gate. Verify
the generated package identity, `gitHead`, exports and runtime contract, then
npm-pack that verified directory and record the archive SHA-256. The generated
manifest sets `publishConfig: { access: "public", tag: "routing" }`.

Only after explicit publication authorization, use the verified package with an
explicit routing tag:

```bash
npm publish ./dist/npm/flapsdk-vault-runtime-0.1.40-beta.routing.0.tgz --access public --tag routing
```

Read back the exact package version, `gitHead`, integrity and all dist-tags;
`latest` and `next` must be unchanged. The tests and docs in this preparation
commit do not establish npm publication or deployment.

## Consumer and source-package boundaries

After registry verification, an isolated consumer branch can install the exact
package with `yarn add --exact @flapsdk/vault-runtime@0.1.40-beta.routing.0`.
Validate package feature flags, hook/adapter support, existing Apps, direct
entry/refresh, same-App state persistence, native history and unknown routes.
Deploy receiving host support before accepting route-dependent artifacts.

This is a **runtime-only** testing channel. `app:*`, `vault:*`, App/Vault source
ZIP provenance and production acceptance keep their existing official
main/latest rules. This prerelease cannot create a publicly accepted App source
ZIP or satisfy the stable runtime/hash contract in a production consumer. Those
checks must continue to reject it. Private canaries remain private and
unpublishable; `runtime:test:canary` intentionally accepts only protected canary
archives. Neither mechanism grants publication/deployment permission.

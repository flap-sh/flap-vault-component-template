## Included behavior

Standalone Mini App v2 gains `useMiniAppRouter()` with App-relative `pathname`,
decoded immutable `segments`, `search`, and `push/replace/back`. Hosts supply
browser or memory adapters. Generic paths such as `/apps/{slug}/bnb/{ca}` and
`/apps/{slug}/settings` keep the same reviewed artifact and wallet/session.
Paths do not grant contract permissions; existing target/resolver policies apply.

Browser navigation retains App state and framework history, supports direct
entry, refresh and native back/forward, and rejects path escapes. Workbench
previews use isolated memory history. The source checker requires a supporting
Runtime for routing imports. When an App invokes `useMiniAppRouter()`, the SDK
compatibility shim checks the routing version/export, and the hook requires a
host-provided adapter. Existing Apps need no adapter and keep working.

No dependencies or manifest fields are added. Runtime contract version 1, Vault
source format 6 / E2E report v2 and standalone App format 7 / E2E report v3 remain
unchanged. Capability identity is `MINI_APP_ROUTING_VERSION=1` and
`sdkFeatures.miniAppRouting=1`.

## Pre-merge validation

Use Node.js 24 and Yarn 1.22 on the routing-only branch from official main:

```bash
yarn test:mini-app-routing
yarn test:release-channel
yarn test:runtime-package-mode
yarn run check
yarn runtime:pack:canary
```

The canary builder requires clean committed source. It marks the package private
and unpublishable, verifies the packed provider/hook context, missing-adapter
failure, host-only adapters and generated README, then records the tarball hash.
Test that exact canary in both consumer projects, including browser routing and
production builds. A canary cannot supply source-ZIP provenance or be published.
The dedicated Mini App v2 workflow and ordinary CI both run the routing suite.

## Publication gate and evidence still required

Maintainer npm authentication must be usable before merging the release into
official main. Publication remains blocked until that authentication and the
reviewed official-main release build are available. No trusted publication
workflow is introduced by this change. Keep official main and npm tags unchanged
while this gate is unresolved.

After authorization, merge the reviewed release and use a clean checkout of that
exact fetched official-main commit. Fork maintainers set
`FLAP_TEMPLATE_FRESHNESS_REF=upstream/main` with an official upstream remote:

```bash
FLAP_TEMPLATE_FRESHNESS_REF=upstream/main yarn runtime:package
yarn runtime:verify-package
yarn test:runtime-provider --package
```

Inspect version `0.1.40`, the exact reviewed main `gitHead`, public `latest`
publish configuration, routing exports/README and absence of private/canary

SHA-256 and npm integrity here after publication; they are **pending**, not the
hashes of a feature-branch canary. Verify the downloaded bytes, registry identity

## Consumer rollout

After registry verification, pin exact `@flapsdk/vault-runtime@0.1.40` in Workbench
and the Flap host. Synchronize Workbench validation inputs, the source checker,
hook-invocation compatibility shim, isolated preview routing and host
adapter/version checks. Deploy supporting hosts before accepting
routing-dependent App source ZIPs.
App authors then regenerate check/E2E/package/verification proof using the exact
published identity. A local version bump or npm publication alone does not deploy
hosts, authorize wallet actions or approve an artifact.

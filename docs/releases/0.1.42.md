## Behavior and compatibility

Add this exact reviewed query prefix:

```text
https://bsc-testnet-debug.butterfly.army/fsi/v1
```

The SDK and template source checker recognize three FSI roots. When more than one is declared, selection uses this priority, independently of manifest array order and `chainId`:

1. `https://fsi.taxed.fun/fsi/v1`
2. `https://bsc-debug.butterfly.army/fsi/v1`
3. `https://bsc-testnet-debug.butterfly.army/fsi/v1`

Existing mainnet preference and the legacy URL-builder default remain unchanged. A testnet artifact should declare only the testnet FSI root in `manifest.endpoints`. `sdk.readFsi(relativePath, params)` uses the declared root; changing the wallet or SDK chain does not select a different FSI deployment. Failed requests do not retry against another host.

```json
{ "endpoints": "https://bsc-testnet-debug.butterfly.army/fsi/v1" }
```

The root declaration must have no query string; an optional trailing slash is accepted. A domain-only declaration or a particular child endpoint does not satisfy `sdk.readFsi` authorization. The allowance covers only each exact HTTPS origin and `/fsi/v1` or its child paths. It does not add a `butterfly.army` wildcard or authorize `/fsi/versions`, `/fsi/v10`, images, navigation or frames. Credentials, fragments, alternate ports, lookalike hosts, raw/encoded dot segments and encoded path separators remain rejected before URL normalization.

SDK reads retain GET, omitted credentials, rejected redirects, no referrer and no-store caching. Direct static or templated FSI `fetch` calls still require literal `method: "GET"`, `credentials: "omit"`, `redirect: "error"` and `referrerPolicy: "no-referrer"`; optional `cache: "no-store"` is allowed, while headers, bodies and option overrides remain blocked. Only query values encoded with the global `encodeURIComponent` may vary in a raw fetch; dynamic paths use `sdk.readFsi`. Manifest declarations and endpoint review evidence remain required. See [FSI usage and boundaries](../sdk.md#fsi-queries).

No new dependency, public SDK API, export, manifest field or wallet permission is introduced. SDK signatures, runtime contract version 1, Vault source format 6 / E2E v2 and standalone App source format 7 / E2E v3 remain unchanged. The npm runtime contains the SDK implementation, while source-checker rules are deployed separately.

## Consumer and checker rollout

After publication, update the Flap host and Workbench to the exact published runtime version with their Yarn lockfiles, then deploy them. Workbench must also synchronize its mirrored FSI policy/checker, source-review output and template validation-input contracts to this release; installing the npm runtime alone does not deploy the receiving source checker or its provenance inputs. Retain the declared endpoint and human-review requirements.

Source authors then update the official template and regenerate check, guest/connected E2E, source-package and verification evidence against the new published identity. Existing `0.1.41` provenance cannot certify changed SDK inputs, and a private canary cannot replace stable App/Vault package provenance. Validate the actual testnet query and browser CORS after the matching consumers and checker are deployed, and retain mainnet routing regression checks. These deployments and artifact approvals are separate work from this prepared release.

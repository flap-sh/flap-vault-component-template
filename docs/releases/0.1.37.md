# 0.1.37 — Controlled dynamic IPFS content

[简体中文](0.1.37.zh-CN.md)

This is the release target for the dynamic IPFS feature merged in
[PR #24](https://github.com/flap-sh/flap-vault-component-template/pull/24).
Source changes and a release PR do not mean the npm version has been published;
confirm registry metadata before upgrading production dependencies.

## Changes

- `sdk.readIpfsText(cid, path?)` returns bounded UTF-8 text or JSON as a string.
- `IpfsText` displays escaped plain text and handles loading, failure, and CID changes.
- `IpfsImage` accepts dynamic bare CIDs, including values from FSI or SDK uploads.
- `IPFS_CONTENT_VERSION === 1` and `runtime-contract.sdkFeatures.ipfsContent === 1`
  identify the capability. Dynamic sources remain subject to manual review.

See the [API guide](../ipfs-content.md) for examples and limits. Fixed platform
gateways, safe CID/path validation, redirect rejection, omitted credentials,
bounded reads, and escaped text rendering remain part of the runtime boundary.
`IpfsBackground` stays static CID-only; `NftMetadataImage` remains a separate path.
No dependencies, manifest fields, contract write permissions, or schema/package
format/runtime contract versions are added or changed in this release preparation.

## Compatibility and rollout

| Runtime | FSI queries and reviewed resolved `execute` | IPFS text API/component and dynamic image checker |
| --- | --- | --- |
| `0.1.35` | Unsupported | Unsupported |
| `0.1.36` | Supported | Unsupported |
| `0.1.37` | Supported, unchanged | Supported with matching Workbench policy |

After npm publication:

1. Pin `@flapsdk/vault-runtime@0.1.37` in Workbench and the Flap host using Yarn,
   and commit their lockfile changes. Do not record private canaries as release dependencies.
2. Deploy the matching Workbench IPFS checker and runtime capability gate.
   Upgrading the npm package alone does not replace Workbench's checker scripts.
3. Deploy both upgraded hosts before accepting new text/dynamic-image artifacts.
   Keep artifact imports on `@/src/sdk` and `@/src/ui`.
4. Verify a paginated FSI result containing text/image CIDs, loading/error states,
   and CID changes. SDK uploads can generate test data when the existing upload
   service is configured; no project-specific business data is required.

Text reads use browser requests to platform gateways and require those gateways
to serve the pinned content with browser-compatible access. They need no new
host route or Pinata credential. Uploads retain the existing host-owned
`/api/runtime/upload` service and server-side configuration. Automated upload
fixtures are mocked; they do not replace live upload/gateway verification.

## Maintainer publication

Follow [Versioning](../versioning.md#stable-release-workflow): merge the version
and documentation update, build and verify from the exact official `main` head,
test the generated runtime entrypoints, then pack that verified directory.
Publish only after maintainer authorization, and verify registry version,
`gitHead`, integrity, and dist-tags against the packed archive. Keep `next`
unchanged. Never publish a private `-canary.*` tarball.

## 测试内容

独立 App 使用 `useMiniAppRouter()` 获取 App 相对路径、只解码一次的不可变
segments、查询参数与 push/replace/back。浏览器或内存适配器由宿主提供。
兼容 shim 在新 hook 被调用时检查版本/导出，hook 要求宿主注入适配器。
源码检查器识别常见静态 routing 导入、默认 SDK 别名和 SDK 转导出；它不执行通用
JavaScript 数据流分析。Runtime contract version 1、
`sdkFeatures.miniAppRouting=1`、既有钱包/合约权限与 manifest schema 保持不变。
详见[API 文档](../mini-app-routing.zh-CN.md)。

## 构建与发布门槛

仅允许 `@flapsdk/vault-runtime`、`X.Y.Z-beta.routing.N` 版本，以及官方
`flap-sh/flap-vault-component-template` 的 `feat/mini-app-routing` 分支。
本地必须是干净、已提交且与刚抓取的官方分支完全相同的源码。fork 维护者显式选择
官方 `upstream`：

```bash
FLAP_TEMPLATE_FRESHNESS_REF=upstream/feat/mini-app-routing yarn runtime:package:routing
yarn runtime:verify-package
```

专用命令不接受 App 文件夹、canary 参数，也不接受跳过新鲜度或自动同步参数。
首次发布只允许在固定公共 npm registry 对 `routing` 返回真实 HTTP 404、
dist-tags 中不存在 `routing`、精确目标版本也返回 HTTP 404 时继续。源码还必须包含
有效的 npm latest 已发布 `gitHead`，latest 元数据必须与 dist-tags 一致。
重定向、超时、鉴权错误、其它 HTTP 错误或无效元数据都会阻断，不能当成缺失。
后续版本只比较 routing 自身版本，并要求包含 routing 已发布 `gitHead`；不与 next 比较。

先审核并把源码推送到官方路由分支，再运行上述命令；本地准备分支不满足 exact-ref
门槛。核对生成包的版本、`gitHead`、导出与 runtime contract，再对已核验的目录
执行 npm pack 并记录归档 SHA-256。生成 manifest 固定
`publishConfig: { access: "public", tag: "routing" }`。

已获授权的发布使用已核验归档，并显式指定 routing 标签（以下作为发布记录，此版本不可重复发布）：

```bash
npm publish ./dist/npm/flapsdk-vault-runtime-0.1.40-beta.routing.0.tgz --access public --tag routing
```

发布后已通过公共 registry 回读精确版本、`gitHead`、integrity 和归档字节；
`latest`、`next` 均保持原值，完整结果见上方记录。npm 包发布不代表消费者已部署。

## 消费者与源码包边界

registry 核验后，可在隔离消费者分支中使用
`yarn add --exact @flapsdk/vault-runtime@0.1.40-beta.routing.0` 安装。
验证能力标记、hook/适配器支持、旧 App 兼容、深链直入/刷新、同 App 状态保留、
原生历史与未知路由。接收依赖路由的新 artifact 前先部署支持宿主。

这是 **runtime-only 测试通道**。`app:*`、`vault:*`、App/Vault 源码 ZIP 来源以及
生产接收仍按官方 main/latest 规则执行。此预发布版不能生成公开接收的 App 源码 ZIP，
也不能满足生产消费者的 stable runtime/hash 契约；这些检查应继续拒绝它。
私有 canary 仍保持私有且不可发布，`runtime:test:canary` 刻意只接受受保护的 canary
归档。两种机制均不授予额外发布或部署权限。
